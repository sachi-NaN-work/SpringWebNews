### ＜ 1 ＞ 開発の進め方

最初からすべての機能を作るのではなく、機能を小さく分けて段階的に開発した。  
まず、ログイン、トップ画面、ニュース閲覧などの基本機能を作成し、その後、管理画面、推薦機能、学習機能を追加した。

機能を追加する際は、どのような処理を追加する必要があるかを ChatGPT に確認しながら進めた。  
回答内容をそのまま使うのではなく、必要な部分を取り入れて実装した。

機能を追加するたびに、画面表示や画面遷移、データが想定通りに表示されているかを確認した。  
不具合が発生した場合は、ログから原因を確認し、修正後に再度動作確認する形で進めた。  
また、正常に動作していた状態との差分を確認し、どの変更が原因になったかを一つずつ切り分けた。

外部端末からも接続できるように、まずホスト PC で動作を確認し、その後、外部公開と URL の固定化を行った。

### ＜ 2 ＞ 開発で工夫したこと

#### ＜処理ごとに役割を分けたこと＞

三層アーキテクチャを参考にし、処理の役割に応じて、プレゼンテーション層・アプリケーション層・データ層・設定層などに分けて実装した。  
役割ごとに処理を分けることで、どこで何をしているか分かりやすくし、プログラム把握や修正もしやすい構成にした。


<br>


#### ＜データの用途に応じて保存先を分けたこと＞

ユーザーやニュースなど継続して保存するデータは PostgreSQL、頻繁に参照・更新する情報は Redis、利用者の操作履歴は Kafka と、用途に応じて使い分けた。  
それぞれの役割を分けることで、処理の流れを整理しやすくした。

### ＜ 3 ＞ 開発で苦労したことと対応

#### ＜Spring Boot を使った Web 開発＞

**・苦労したこと**

Spring Boot を使った Web 開発の経験が浅い状態からの開発だったため、  
基本的な仕組みや使い方を調べながら実装する必要があった。  
画面遷移処理や認証・認可など確認する内容が多く、処理の流れを理解することに苦労した。


<br>


**・苦労したことへの対応**

Spring Boot の基本的な仕組みや実装方法を調べながら、一つずつ動作を確認して開発を進めた。  
不明点は ChatGPT に「実現したいこと」や「コードの修正箇所」を確認し、実際のコードと動作を確認しながら理解を深めた。

### ＜ 4 ＞ 開発によって得られたもの

#### ＜Spring Boot を使った Web 開発の経験＞

これまでの Java の開発経験を活かしながら、Web アプリ開発を経験できた。  
Java の処理だけでなく、Cloudflare Tunnel を使った外部公開の方法など、  
Web アプリ全体の流れを意識して実装する経験につながった。


<br>


#### ＜Docker を使った環境構築の経験＞

PostgreSQL、Redis、Kafka などを Docker Compose でまとめて起動することで、  
複数の環境を同じ設定で管理する基本的な流れを理解できた。


<br>


#### ＜トラブルシューティングの経験＞

Docker を起動した状態で PC が予期せず強制終了した後、  
コマンドプロンプトでは対象ポートが未使用と表示されているにもかかわらず、  
Docker の起動時にはポートが使用中というエラーが発生することがあった。

Docker や Windows 側に強制終了前のネットワーク状態が残っている可能性を考え、  
PC を再起動したところエラーが解消した。


<br>


#### ＜データの用途に応じて使い分ける経験＞

PostgreSQL と Redis を実際に組み合わせることで、すべてのデータを同じ場所に保存するのではなく、  
用途に応じて使い分ける考え方を学んだ。


<br>


#### ＜Kafka を使った処理連携の経験＞

閲覧や Good、Bad などの利用者操作を Kafka に送り、後続処理へ渡す構成を実装した。  
処理を直接つなぐ方法だけでなく、イベントを使って処理を連携する方法を経験できた。


<br>


#### ＜画面表示時の権限制御の考え方＞

管理画面のリンクやボタンを表示しない画面上の制御だけでなく、  
URL に直接アクセスされた場合を考慮して、処理側でも権限を確認する必要があることを学んだ。


<br>


#### ＜ログインロックの仕組み＞

ログインに一定回数失敗した場合に、一時的にログインを制限するログインロックを実装した。  
Redis にユーザーごとのログイン失敗回数とロック状態を保持し、一定時間経過後に解除する仕組みを通して、  
繰り返しのログイン試行に対する認証セキュリティの基本的な考え方を学んだ。


<br>


#### ＜無操作タイムアウトの仕組み＞

一定時間ユーザー操作がない場合にログアウトする無操作タイムアウトを実装した。  
複数タブを開いている場合は最終操作時刻を共有し、共有できない場合でもタブ単位でタイムアウト判定を継続する仕組みを通して、  
利用者の操作状況を考慮したセッション管理の考え方を学んだ。


<br>


#### ＜A / B テストの考え方＞

推薦処理で利用者を A / B のグループに分け、グループごとに推薦内容の割合を変える仕組みを実装した。  
同じユーザーが継続して同じグループになるように割り当てることで、条件を分けて処理結果を比較する A / B テストの基本的な考え方を学んだ。


<br>


#### ＜学習に必要なデータ量の考え方＞

機械学習に必要なデータ量の目安としてパラメータ数の 10 倍以上のデータを最低限の目安とする  
「バーニーおじさんのルール」という経験則を学んだ。
