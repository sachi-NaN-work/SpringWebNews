## 2. システム概要

ニュース記事の閲覧、カテゴリ・ハッシュタグ別表示、お気に入り、Good / Bad ボタン等による推薦を提供する Web アプリ。

## 3. システム目的

- ニュース記事を登録・閲覧できるようにする


- ログイン機能により、操作ユーザーを特定できるようにする


- ログインユーザーの行動傾向を記録・確認できるようにする

    - ニュース記事の閲覧
    - カテゴリ別の閲覧傾向
    - ハッシュタグ別の閲覧傾向
    - お気に入り登録
    - Good / Bad ボタンによるリアクション


- 個人ユーザーの行動傾向・全体ユーザーの行動傾向をもとに、おすすめニュースを提示する


- 管理者・担当者が、ユーザー、ニュース、カテゴリ、ハッシュタグ、学習モデルを管理できるようにする

## 4. アプリのユーザー種別

| ユーザー種別   | 説明                                 |
|----------|------------------------------------|
| 一般ユーザー   | ニュース閲覧、パスワード変更等が可能。                |
| ユーザー管理者  | ユーザー作成、ロール変更等が可能。                  |
| 学習モデル管理者 | 学習モデル作成、読込等が可能。                    |
| ニュース管理者  | ニュースの作成・編集等が可能。                    |
| デモユーザー   | デモ用ユーザー。学習モデル作成、読込等が可能。パスワード変更は不可。 |
| 管理者      | 全権限を持つ管理者。管理者の無効化・ロール変更・削除は不可。     |

## 7. システム構成

### 7.1 レイヤー構成

| レイヤー       | 実装パッケージ                        | 役割                                                   |
|------------|--------------------------------|------------------------------------------------------|
| プレゼンテーション層 | `com.news.recapp.presentation` | ユーザーからの入力を受け取り、画面や API の処理結果を返却する                    |
| アプリケーション層  | `com.news.recapp.application`  | ニュース表示、推薦、登録、管理などの業務処理を実行し、外部処理との呼び出し方法を定義する         |
| データ層       | `com.news.recapp.data`         | PostgreSQL、Redis、Kafka、ONNX 等との接続処理を実装する             |
| DB アクセス層   | `com.news.recapp.persistence`  | PostgreSQL に保存するデータの構造と、データを検索・保存する Repository を定義する |
| 設定層        | `com.news.recapp.config`       | セキュリティ、DB、Redis、Kafka 等の設定を定義する                      |
| 学習処理       | `training/`                    | Python で推薦モデルの学習と学習済みモデルの出力を行う                       |


<br>


### 7.2 技術構成

| 分類         | 技術                                  |
|------------|-------------------------------------|
| バックエンド     | Java / Spring Boot / Spring WebFlux |
| セキュリティ     | Spring Security（Reactive）           |
| DB         | PostgreSQL                          |
| キャッシュ・状態保存 | Redis                               |
| メッセージング    | Kafka                               |
| フロントエンド    | Thymeleaf / HTML / CSS / JavaScript |
| 機械学習       | Python / ONNX / ONNX Runtime        |
| コンテナ       | Docker / Docker Compose             |


<br>


### 7.3 主要技術の説明

| 技術              | 説明                       | 使用理由                                  |
|-----------------|--------------------------|---------------------------------------|
| Spring Boot     | Webアプリ開発の基盤              | Java で Web アプリを効率よく構築できるため            |
| Spring WebFlux  | 非同期処理に対応した Web 機能        | DB や Redis などの処理待ちでアプリ全体が止まらないようにするため |
| Spring Security | ログインや権限チェックを行う機能         | 認証・認可を安全に実装するため                       |
| Thymeleaf       | HTML 画面を表示するテンプレート機能     | Spring Bootと組み合わせて画面を作りやすいため          |
| PostgreSQL      | ニュースやユーザー情報を保存するDB       | リレーショナルデータを安定して管理できるため                |
| Redis           | お気に入りや推薦用データを一時保存する仕組み   | 高速に読み書きでき、ランキングや一時データ管理に向いているため       |
| Kafka           | ユーザー操作イベントを送信する仕組み       | ユーザー操作を非同期に処理し、推薦処理へ連携しやすくするため        |
| ONNX            | 学習済みモデルを利用するための保存形式      | Python で学習したモデルを Java 側で利用しやすくするため    |
| Python          | 推薦モデルの学習処理に使用する言語        | 機械学習ライブラリを利用するため                      |
| JavaScript      | 画面上のボタン操作や API 送信に使用する言語 | お気に入りや Good / Bad 操作を画面遷移なしで行うため      |
| Docker Compose  | DB などの関連サービスをまとめて起動する仕組み | 開発環境を簡単に再現できるようにするため                  |

## 8. 外部連携

| 連携先          | 用途                                                |
|--------------|---------------------------------------------------|
| PostgreSQL   | ニュース、カテゴリ、ハッシュタグ、ユーザー、権限、フィードバック等のデータを保存・取得する     |

| ファイルシステム     | 推薦モデルファイル、固定係数、学習結果、学習ログ等を保存・取得する                 |

## 10. 非機能要件

### 10.1 非機能要件一覧

| 区分         | 要件                                          |
|------------|---------------------------------------------|
| 性能         | ニュース一覧・詳細は通常条件で数秒以内に表示する                    |
| 可用性        | Docker Compose で関連サービスをまとめて起動できる            |
| セキュリティ     | パスワードはハッシュ化した形式で保存し、平文では保存しない               |
| 認証制御       | 未ログイン時は指定された許可パス以外を認証必須とする                  |
| 認可制御       | 管理機能は `@PreAuthorize` で権限コード単位に制御する         |
| 保守性        | 画面処理、業務処理、外部連携、DB 操作の役割を分けて実装する             |
| データ整合性     | ニュース本文やハッシュタグの登録ルールを DB 側でもチェックする           |
| 推薦耐障害性     | 学習済みモデルが利用できない場合でも、固定係数や基本スコアを利用して推薦を継続する   |
| 補助処理耐障害性   | 補助処理が失敗した場合でも、独立して実行可能な処理を継続する              |
| フィードバック整合性 | PostgreSQL へのフィードバック保存に失敗した場合は成功扱いとしない      |
| タイムアウト耐障害性 | 複数タブ間で最終操作時刻を共有できない場合でも、タブ単位で無操作タイムアウトを継続する |
| 検証性        | ダミーデータで主要機能を試せるようにする                        |
| ログ         | DB、Kafka、モデル、入力エラーなどの調査用ログを出力する             |


<br>


### 10.2 処理継続方針

ユーザーが直接要求した処理を主処理とし、主処理に付随して実行する推薦用情報更新、イベント送信、操作記録等を補助処理として扱う。

補助処理に失敗した場合は、必要な警告ログを出力したうえで、完了済みの主処理を取り消さず、独立して実行可能な後続処理を継続する。
