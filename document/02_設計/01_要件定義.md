## 2. システム概要

### 2.1 システムの目的

本システムは、転職活動において Spring を用いた Web アプリケーション開発力と、  
設計などの上流工程の理解を示すポートフォリオとして開発する。  
また、機械学習（推薦機能の学習）のスキルを身につける目的として、ユーザーの行動傾向をもとに、  
おすすめのリンク先を提示できる仕組みを取り入れる。


開発の題材には、利用者が身近に感じやすく、機能のイメージもしやすい　**『ニュースサイト』** を選定した。  
『ニュースサイト』は日常的に利用されるサービスであり、記事閲覧やおすすめ表示の流れをイメージしやすい。  
そのため、推薦機能を組み込んだポートフォリオとして適していると判断した。  
（※）『EC サイト』も候補にあったが、金額表示や購入操作を含むデモサイトは利用者が操作をためらう可能性があるため、今回は対象外とした。


実務に近い構成のアプリケーションとして設計・実装することを目指すため、ログイン処理、Docker 等を実装・使用する。


（補足）転職活動が終了しても、実際の開発現場に参考資料として、部下にも開発の手本となるような成果物とする。

## 3. ユーザー

### 3.1 ユーザー区分

| ユーザー区分   | 内容                                            |
|----------|-----------------------------------------------|
| 一般ユーザー   | ニュース参照、おすすめニュース参照、お気に入り、Good・Bad、パスワード変更を利用する |
| ユーザー管理者  | 一般ユーザーの機能に加え、ユーザーの作成、有効・無効変更、ロール変更を行う         |
| ニュース管理者  | 一般ユーザーの機能に加え、ニュース、カテゴリ、ハッシュタグを管理する            |
| 学習モデル管理者 | 一般ユーザーの機能に加え、学習モデルの学習、再読込、アップロードを行う           |
| 管理者      | すべての管理機能を利用する                                 |
| デモユーザー   | デモ用として定めた学習モデル管理機能を利用する                       |

<br>

### 3.2 ユーザー認証

| 項目        | 要件                               |
|-----------|----------------------------------|
| ログイン      | ユーザー ID とパスワードで認証する              |
| ログアウト     | ユーザーがログイン状態を終了できる                |
| ユーザー状態    | 無効なユーザーはログインできない                 |
| ログインロック   | ログイン失敗回数が上限に達したユーザーは一定時間ログインできない |
| 無操作タイムアウト | 一定時間操作がない場合はログイン状態を終了する          |
| パスワード保存   | パスワードは復元できない形式で保存する              |
| 権限制御      | ユーザーに設定されたロールと権限に応じて利用可能な機能を制御する |

## 4. 対象範囲

### 4.1 対象機能

| 分類       | 対象機能                                             |
|----------|--------------------------------------------------|
| 認証・認可    | ログイン、ログアウト、ログインロック、無操作タイムアウト、ロール・権限制御            |
| ニュース参照   | 最新ニュース、全ニュース、カテゴリ別ニュース、ハッシュタグ別ニュース、ニュース詳細        |
| ユーザー操作   | お気に入り登録・解除、Good・Bad・評価解除、フィードバック登録               |
| 推薦       | おすすめニュースの取得、推薦値による並び替え、A / B 区分、再閲覧抑制、カテゴリ偏り制御   |
| ユーザー管理   | ユーザー作成、有効・無効変更、ロール変更、パスワード変更                     |
| ニュース管理   | ニュース作成、有効・無効変更                                   |
| カテゴリ管理   | カテゴリ作成、有効・無効変更                                   |
| ハッシュタグ管理 | ハッシュタグ作成、有効・無効変更、ニュースへの関連付け                      |
| 学習モデル管理  | 学習実行、モデル再読込、モデルアップロード                            |
| 監視       | アプリケーションの稼働状況と接続状態の確認（例：`/actuator/health`）      |
| システム情報   | アプリケーションのバージョンやビルド情報の確認（例：`/actuator/info`）      |
| API 仕様   | API の接続先や送受信するデータの確認（例：`/swagger-ui/index.html`） |


<br>


### 4.2 対象外

| 分類       | 対象外とする内容                        |
|----------|---------------------------------|
| 利用端末     | スマートフォン専用画面                     |
| コメント     | ニュースへのコメント投稿・管理                 |
| ニュース収集   | 外部ニュースサイトからの記事自動収集              |
| ユーザー登録   | 一般ユーザーによる自己登録                   |
| パスワード再発行 | メール等を利用したパスワード再発行               |
| 物理削除     | 画面からのカテゴリ、ニュース、ハッシュタグ、ユーザーの物理削除 |
| 固定係数登録   | 管理画面からの固定係数ファイルのアップロード          |

## 5. 機能要件

### 5.1 ログイン機能

| 要件ID        | 要件                                                            |
|-------------|---------------------------------------------------------------|
| FR-AUTH-001 | ユーザー ID とパスワードを入力してログインできること                                  |
| FR-AUTH-002 | 認証成功時はトップ画面を表示すること                                            |
| FR-AUTH-003 | 認証失敗時はログイン画面にエラーを表示すること                                       |
| FR-AUTH-004 | ログインロック中はログインできないことを表示すること                                    |
| FR-AUTH-005 | ログアウト後はログイン画面を表示すること                                          |
| FR-AUTH-006 | 一定時間操作がない場合はタイムアウト画面を表示すること                                   |
| FR-AUTH-007 | 認証不要として定義した画面、API、静的ファイルはログインせずに利用できること                       |
| FR-AUTH-008 | その他の画面と API は原則としてログインを必要とすること                                |
| FR-AUTH-009 | 複数タブ間で最終操作時刻を共有する機能を利用できない場合でも、<br/>タブ単位で無操作タイムアウトの判定を継続できること |

<br>


### 5.2 トップ画面・ニュース参照

| 要件ID        | 要件                               |
|-------------|----------------------------------|
| FR-NEWS-001 | トップ画面に最新ニュースを表示できること             |
| FR-NEWS-002 | 公開対象のニュースを一覧表示できること              |
| FR-NEWS-003 | 有効なカテゴリを一覧表示できること                |
| FR-NEWS-004 | 選択したカテゴリのニュースを表示できること            |
| FR-NEWS-005 | 選択したハッシュタグのニュースを表示できること          |
| FR-NEWS-006 | ニュースのタイトル、本文、カテゴリ、ハッシュタグを表示できること |
| FR-NEWS-007 | 無効なニュースを一般画面と推薦結果へ表示しないこと        |
| FR-NEWS-008 | 無効なカテゴリを一般画面とニュース作成時の選択肢へ表示しないこと |
| FR-NEWS-009 | おすすめニュースをトップ画面とニュース詳細画面に表示できること  |
| FR-NEWS-010 | お気に入りニュースをトップ画面とニュース詳細画面に表示できること |


<br>


### 5.3 お気に入り

| 要件ID       | 要件                                                                |
|------------|-------------------------------------------------------------------|
| FR-FAV-001 | ユーザーがニュースをお気に入りへ登録できること                                           |
| FR-FAV-002 | 登録済みニュースをお気に入りから解除できること                                           |
| FR-FAV-003 | お気に入りの登録・解除の応答として、現在のお気に入り状態と登録件数を返却すること                          |
| FR-FAV-004 | お気に入りの登録上限を設定ファイルから変更できること                                        |
| FR-FAV-005 | お気に入りの登録・解除を推薦用のユーザー情報へ反映すること                                     |
| FR-FAV-006 | お気に入りの登録・解除が成功した場合、付随するフィードバック記録に失敗しても、<br/>お気に入りの登録・解除結果を有効とすること |


<br>


### 5.4 フィードバック

| 要件ID      | 要件                                                                                                                                    |
|-----------|---------------------------------------------------------------------------------------------------------------------------------------|
| FR-FB-001 | ニュースの閲覧、選択、お気に入り、Good、Bad、評価解除等の操作を登録できること                                                                                            |
| FR-FB-002 | フィードバックとして、対象ニュースを識別する`ニュースID`、個々の操作内容を示す`操作種別`、<br/>どの画面・経路からの操作かを示す`表示元`、個々の操作を識別する`イベントID`、<br/>その操作につながった要求を追跡する`リクエストID`を受け付けること |
| FR-FB-003 | フィードバックをユーザー、ニュース、カテゴリ、操作種別、操作日時とともに保存すること                                                                                            |
| FR-FB-004 | 通信再送などで同一の`イベントID`を持つフィードバックを複数回受信した場合でも、1件のみ登録すること                                                                                   |
| FR-FB-005 | フィードバックを Kafka へ送信できること                                                                                                               |
| FR-FB-006 | フィードバックをカテゴリおよびハッシュタグ単位の推薦情報へ反映すること                                                                                                   |
| FR-FB-007 | 未認証のユーザーからの登録要求を受け付けないこと                                                                                                              |
| FR-FB-008 | ニュースの閲覧、選択等に伴う自動フィードバックの送信に失敗した場合でも、<br/>ニュース表示や画面遷移等のユーザー操作を継続できること                                                                  |
| FR-FB-009 | 推薦用情報の更新または Kafka への送信に失敗した場合でも、<br/>実行可能なフィードバック保存処理を継続すること                                                                          |
| FR-FB-010 | Good、Bad、評価解除等の明示的なフィードバックは、<br/>フィードバックの保存に失敗した場合に成功扱いとしないこと                                                                         |


<br>


### 5.5 推薦

| 要件ID       | 要件                                               |
|------------|--------------------------------------------------|
| FR-REC-001 | ユーザーごとにおすすめニュースを取得できること                          |
| FR-REC-002 | 取得件数を指定できること                                     |
| FR-REC-003 | 取得件数が未指定または 0 以下の場合は設定された標準件数を使用すること             |
| FR-REC-004 | A / B 区分をユーザー名の指定文言により区別できること                    |
| FR-REC-005 | A / B 区分はユーザー名の指定文言が無い場合は、ユーザー ID を基に固定的に割り当てること |
| FR-REC-006 | 公開中のニュースのみを推薦対象とすること                             |
| FR-REC-007 | ユーザーの閲覧、お気に入り、Good、Bad の傾向を推薦へ反映すること             |
| FR-REC-008 | ニュースのカテゴリとハッシュタグを推薦へ反映すること                       |
| FR-REC-009 | 個人候補と全体候補から推薦記事を選択すること                           |
| FR-REC-010 | 推薦値の高い順に並べること                                    |
| FR-REC-011 | 同一カテゴリの記事に偏りすぎないようにすること                          |
| FR-REC-012 | 同じユーザーが繰り返し閲覧した記事の推薦値を下げること                      |
| FR-REC-013 | 学習済みモデルを利用できる場合はモデル評価を推薦値へ反映すること                 |
| FR-REC-014 | 学習済みモデルを利用できない場合は固定係数を利用すること                     |
| FR-REC-015 | 学習済みモデルと固定係数を利用できない場合は基本評価のみで推薦値を算出すること          |
| FR-REC-016 | 推薦結果として推薦記事一覧、A / B 区分、処理時間を返すこと                 |

### 6.1 PostgreSQLへ保存するデータ

| データ           | 内容                                |
|---------------|-----------------------------------|
| カテゴリ          | カテゴリ ID、識別名、カテゴリ名、有効状態            |
| ニュース          | ニュース ID、カテゴリ ID、公開日時、有効状態         |
| ニュース内容        | ニュース ID、タイトル、本文                   |
| ハッシュタグ        | ハッシュタグID、ハッシュタグ名、有効状態             |
| ニュース・ハッシュタグ関連 | ニュース ID、ハッシュタグ ID                 |
| フィードバック       | ユーザー ID、ニュース ID、カテゴリ ID、操作種別、操作日時 |
| ユーザー          | ユーザー ID、パスワード、ロール、有効状態、登録日時       |
| ロール           | ロールコード、ロール名                       |
| 権限            | 権限コード、権限名                         |
| ロール・権限関連      | ロールコード、権限コード                      |


<br>


### 6.2 Redisへ保存するデータ

|---------------|------------------------------|

| ユーザー別ニュース閲覧情報 | ユーザーごとのニュース閲覧回数              |
| ユーザー別カテゴリ情報   | 閲覧、お気に入り、Good、Bad のカテゴリ別集計   |
| ユーザー別ハッシュタグ情報 | 閲覧、お気に入り、Good、Bad のハッシュタグ別集計 |
| ユーザー別操作合計     | ユーザーごとの操作種別別合計               |
| 全体ニュース閲覧情報    | A / B 区分ごとのニュース閲覧回数          |
| 全体カテゴリ情報      | カテゴリごとの操作集計                  |
| 全体ハッシュタグ情報    | ハッシュタグごとの操作集計                |
| 全体操作合計        | 操作種別ごとの全体集計                  |
| フィードバック重複排除情報 | 同一イベントの重複登録を判定する情報           |

| ハッシュタグ        | 原則として物理削除せず、有効状態で管理する |

| ニュース・ハッシュタグ関連 | ニュースとハッシュタグの関連として保持する |

## 10. 入力要件

| 項目          | 要件                           |
|-------------|------------------------------|
| 必須項目        | 未入力、空文字、空白のみを許可しないこと         |
| UUID        | UUID 形式でない値を受け付けないこと         |
| 文字数         | 項目ごとに定めた最大文字数を超えないこと         |
| 選択項目        | 定義済みの値または画面に表示した選択肢のみ受け付けること |
| 重複          | 一意とする項目の重複登録を許可しないこと         |
| パスワード       | 8 文字以上で、英大文字、英小文字、数字を含むこと    |
| パスワード確認     | 新しいパスワードと確認値が一致すること          |
| ニュースタイトル    | 20 文字以内とすること                 |
| カテゴリ識別名     | 10 文字以内とすること                 |
| カテゴリ名       | 10 文字以内とすること                 |
| ハッシュタグ名     | 10 文字以内とすること                 |
| ニュースのハッシュタグ | 有効なハッシュタグを 1 件以上 5 件以下指定すること |
| 学習モデルファイル   | アップロードする場合は ONNX 形式であること     |

## 11. 非機能要件

### 11.1 性能

| 要件ID         | 要件                                       |
|--------------|------------------------------------------|
| NFR-PERF-001 | ニュース一覧、ニュース詳細、推薦結果が通常利用で支障のない時間内に表示されること |
| NFR-PERF-002 | 推薦 API の処理時間を計測できること                     |
| NFR-PERF-003 | ニュース一覧の最大取得件数と推薦結果の最大返却件数を設定できること        |
| NFR-PERF-004 | 外部接続の接続待ち時間と応答待ち時間を設定できること               |
| NFR-PERF-005 | 学習処理の待機時間に上限を設定できること                     |


<br>


### 11.2 可用性

| 要件ID        | 要件                                                        |
|-------------|-----------------------------------------------------------|
| NFR-AVL-001 | 推薦モデルを利用できない場合も固定係数または基本評価で推薦機能を継続できること                   |
| NFR-AVL-002 | アプリケーションの稼働状況を確認できること                                     |
| NFR-AVL-003 | PostgreSQL、Redis、Kafka 等の接続状態を確認できること                     |
| NFR-AVL-004 | 想定外のエラー発生時にユーザー向けエラー画面または API エラーを返すこと                    |
| NFR-AVL-005 | 主処理に付随する補助処理で障害が発生した場合でも、<br/>独立して実行可能な主処理および後続処理を継続できること |


<br>


### 11.3 セキュリティ

| 要件ID        | 要件                                     |
|-------------|----------------------------------------|
| NFR-SEC-001 | パスワードを平文で保存しないこと                       |
| NFR-SEC-002 | 認証が必要な画面と API へ未認証でアクセスできないこと          |
| NFR-SEC-003 | 権限が必要な管理機能を権限のないユーザーが利用できないこと          |
| NFR-SEC-004 | ログイン失敗の繰り返しに対してユーザー単位でロックすること          |
| NFR-SEC-005 | パスワード、API キー、データベース接続パスワード等をログへ出力しないこと |
| NFR-SEC-006 | 本番環境の認証情報を設定ファイルへ直接記載しないこと             |
| NFR-SEC-007 | リクエストの不正な入力値を検証すること                    |


<br>


### 11.4 運用・監視

| 要件ID        | 要件                              |
|-------------|---------------------------------|
| NFR-OPS-001 | 開発環境と本番環境で設定を切り替えられること          |
| NFR-OPS-002 | 共通設定と環境別設定を分離すること               |
| NFR-OPS-003 | アプリケーションログとエラーログを出力すること         |
| NFR-OPS-004 | 推薦件数、処理時間、モデル利用状態を確認できること       |
| NFR-OPS-005 | 学習モデルの最後の操作結果を確認できること           |
| NFR-OPS-006 | Docker を利用して必要なサーバーをまとめて起動できること |
| NFR-OPS-007 | API 仕様画面と監視情報の公開可否を環境ごとに設定できること |


<br>


### 11.5 保守性

| 要件ID        | 要件                                              |
|-------------|-------------------------------------------------|
| NFR-MNT-001 | 業務処理と PostgreSQL、Redis、Kafka、ONNX への接続処理を分離すること |
| NFR-MNT-002 | 共通設定を設定ファイルから変更できること                            |
| NFR-MNT-003 | 画面メッセージを共通管理できること                               |
| NFR-MNT-004 | 単体試験、結合試験、総合試験を実施できる構成とすること                     |
| NFR-MNT-005 | 学習時と推薦時で使用する特徴量の定義を一致させること                      |
